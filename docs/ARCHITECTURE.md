# nim — Marathon アセットビューワー 設計書

対象: Bungie『Marathon』(2026, PC/Steam 版, Tiger エンジン系。tiger-pkg 内のコード名は "Goliath")
言語/基盤: C++23 / MSVC / CMake / Direct3D 12 / Dear ImGui(予定)

## 1. 目標と非目標

**目標**

- ゲーム内の **テキスト・セリフを漏れなく** 取得する(参照を辿るのではなく、全パッケージの全エントリを総当たりで分類する)。
- 3D アセット(静的メッシュ、エンティティ、スケルトン)、マップ、テクスチャ、音声、動画を閲覧・書き出しする。
- **ゲーム本来のシェーディングを再現**する(ゲームのコンパイル済みシェーダ = DXIL をそのまま D3D12 で実行する)。
- 30GB / 650 ファイル規模を前提に、起動・検索・表示が速いこと。

**非目標 / 守ること**

- 起動中のゲームプロセスには一切触れない(BattlEye があるため、メモリ読みやフックはしない)。インストール済みファイルを読み取り専用で開くだけにする。
- ゲームデータや `oo2core_9_win64.dll` を再配布しない。DLL はユーザーのインストールから実行時にロードする。
- 書き出したデータの再配布支援はしない(個人の閲覧・研究・アーカイブ用途)。

## 3. 全体構成

```
nim_app (ImGui UI) ─┬─ nim_render (D3D12)
                    ├─ nim_content (形式ごとのデコーダ)
                    ├─ nim_index (全文検索・参照グラフ・キャッシュ)
                    └─ nim_schema (クラスハッシュ → 構造体定義)
                              │
                         nim_core (パッケージ I/O)          nimcli (バッチ/検証/書き出し)
```

各層は下の層にしか依存しない。`nim_core`〜`nim_content` は GPU にも UI にも依存しないので、CLI とテストからそのまま使える。

### 3.1 nim_core — パッケージ I/O【実装済み】

- `MappedFile`: パッケージはメモリマップで読む(syscall とコピーを避ける)。
- `Package`: ヘッダ、エントリ、ブロック、named tag、hash64 のパース。ブロック単位の「復号 → 展開」パイプライン。パッチを跨ぐブロックは `<name>_<patch>.pkg` を遅延で開く。
- `PackageCipher`: Windows BCrypt の AES-GCM(外部ライブラリ不要)。
- `PackageManager`: install の自動検出(Steam ライブラリ)、最新パッチの選択、言語選択、TagHash / TagHash64 の解決。
- 今後: ブロック LRU キャッシュ(展開済み 256KiB 単位)、スレッドプールでの並列デコード、redacted ブロック用の外部鍵(`keys.txt`)。

### 3.2 nim_schema — タグ構造の型付け

Tiger のタグ(8/0)は「先頭 u64 = サイズ、以降は固定レイアウト + 相対オフセットの配列 / 文字列 / TagHash 参照」という自己記述性の低い形式で、`ref` がクラスハッシュになっている。

- **宣言的スキーマ**: クラスハッシュごとにフィールドのオフセット・型・配列要素型をテーブルで定義する(C++ のマクロ/constexpr テーブル + 実行時に読める JSON の二本立て)。ゲーム更新でオフセットが動いても、コードを書き直さずに定義だけ差し替えられるようにする。
- スキーマは **ビルド ID(ヘッダ 0x28 / 0x18)ごとにバージョン管理** する。Deimos が 1.1.0 で TFX opcode 変更により壊れた事例があるので、更新耐性を最初から設計に入れる。
- **リバースエンジニアリング支援**: 未知クラスに対して、配列ヘッダ候補・TagHash 候補(`0x808xxxxx`)・float 候補・文字列候補を自動で注釈する「タグエクスプローラ」を UI と CLI の両方に用意する。600 種のクラスを人力で埋めていくための道具がこのツールの土台になる。

### 3.3 nim_index — 全件インデックス

- 初回起動時に全エントリのメタデータ(TagHash, type, class, size, パッケージ)と参照グラフ(タグ本文中の TagHash を走査)を作り、`%LOCALAPPDATA%/nim/<build>.nimidx` に保存する。2 回目以降は mmap するだけで即座に起動できる。
- 文字列インデックス: 全言語の全ローカライズ文字列を `string_hash → 各言語のテキスト` で保持し、n-gram の全文検索に対応する(日本語を含む)。
- 逆参照(この文字列 / テクスチャを使っているのは誰か)を引けるようにする。

### 3.4 nim_content — 形式ごとのデコーダ

| 対象 | 方針 |
|---|---|
| テクスチャ | 32/1 ヘッダ(DXGI フォーマット, 寸法, mip, `large_buffer` TagHash)+ 40/1 or 48/1 データ。BC 圧縮はデコードせず GPU に直接上げる。書き出しは DDS(無変換)/ PNG(DirectXTex) |
| ジオメトリ | 頂点/インデックスバッファ(32/40 の 4, 6)+ メッシュタグ(パーツ, LOD, マテリアル参照, 量子化パラメータ)。スケルトン/スキニング。書き出しは glTF 2.0 |
| マテリアル | Technique タグ(ステージごとのシェーダ参照, テクスチャスロット, サンプラ, cbuffer, **TFX バイトコード**) |
| マップ | Activity → Bubble/Map → Static instances / Entity 配置 / Terrain / Decal / Light / Cubemap。数十万インスタンスを前提にする |
| テキスト | ローカライズ文字列コンテナを **総当たりで全列挙**(参照を辿るだけだと孤立した文字列を取りこぼす)。`cipher_shift` の扱いを検証する。全言語を並べて表示 |
| セリフ | ダイアログテーブル(話者, 文字列ハッシュ, WEM / Wwise イベント)を辿り、「字幕テキスト + 話者 + 音声」を 1 行で見られるようにする |
| 音声 | BNK の HIRC を解析してイベント → サウンド → WEM の対応を作る。WEM(Wwise Vorbis/Opus)は vgmstream 相当のデコーダで WAV / OGG にする |
| 動画 | 27/1(USM 推定)を取り出し、外部の ffmpeg で再生/変換する |
| アイテム | investment 系パッケージ(`w64_investment_*`)の定義を表形式にする |

### 3.5 nim_render — D3D12 レンダラ(シェーディング再現の要)

既存ツールのシェーディングが不正確なのは、ゲームのシェーダを捨てて汎用 PBR で描き直しているから。nim では **ゲームの DXIL をそのまま D3D12 パイプラインに渡す**(P4 の最初の検証は `nimshade` で済み。6 章)。

1. **シェーダ**: 41/x の DXIL から PSO を作る。ルートシグネチャは埋め込まれていないので、DXIL のリソース定義(PSV0 / メタデータ)から組み立てる。入力レイアウトはゲームのレイアウト表(class `80808661`)から作る。
2. **TFX バイトコード VM**: マテリアルの cbuffer の値はタグ内のバイトコード式で計算されるので、これをインタプリタで実行して cbuffer を埋める。opcode 表はビルドごとのスキーマに入れる。
3. **スコープ(グローバル cbuffer)**: view, frame, 光源, 大気, 露出などエンジンが供給する定数を再構築する。ここの精度が見た目を左右する。シェーダのリフレクション情報から必要なメンバを洗い出し、意味を一つずつ特定していく。
4. **パス構成**: Tiger の deferred 構成(G-buffer → ライティング → 透過 → ポスト)を再現する。未解明の段階は自前の PBR で代替し、**元シェーダ / 代替の切替と G-buffer の各チャネル表示**をデバッグ表示として用意する。
5. **性能**: bindless ディスクリプタヒープ、コピーキューでの非同期アップロード、テクスチャのストリーミング(mip 単位)、マップのインスタンシング、GPU カリング。

検証方法: ゲームにはデバッガやキャプチャツールを接続できない(BattlEye)ので、同じ視点の **ゲーム内スクリーンショットとの比較** で詰める。

### 3.6 nim_app — UI【一部実装済み: `nim.exe`】

Dear ImGui(docking ブランチ, `third_party/imgui`)を使い、レイアウトと配色は goriath に合わせた(HOME の大ボタン、タブ、パッケージ一覧 + 3D サムネイルのカード + ライブビュー)。UI フォントはゲームのもの(`w64_ui_bootflow` の type 24 エントリが OTF そのもの)を起動時にインストールから読み込み、同梱しない。メッシュの読込とマテリアル評価はワーカースレッド(専用の PackageManager)で行い、UI スレッドは GPU へのアップロードだけを行う。実装済み: メッシュブラウザ(全静的メッシュ、クリックでゲームのシェーダで描画)、テキスト(英語 + 選択言語の並列表示・検索・コピー)、セリフ(話者・台詞・訳・音声イベント)、パッケージエクスプローラ(エントリ表 + hex)、インスペクタ(テクニック・シェーダ・cbuffer・TFX・テクスチャ)、ビュー切替(Lit / G-buffer 各チャネル)、ライト調整、PNG 保存。カタログ(メッシュ一覧・文字列・セリフ)は別スレッドで、専用の PackageManager を使って読む。今後:

- パッケージ / クラス / 種別のツリー、全文検索(テキスト・ハッシュ・TagHash)
- タグエクスプローラ(hex + スキーマ注釈 + 参照の行き来)
- モデル / マップビューワー(元シェーダ ↔ 代替、G-buffer 表示、ライティング切替)
- テキスト / セリフブラウザ(言語並列表示、音声の再生)
- 一括書き出し(glTF, DDS / PNG, WAV / OGG, 文字列の CSV / JSON)

### 3.7 nimcli【一部実装済み】

`pkgs`, `ls`, `types`, `read`, `verify`, `strings`, `dialogue`, `static`, `technique`(TFX の逆アセンブルと VM 実行結果), `shader`(DXIL の取り出し), `extract PKGID TYPE DIR`(種別ごとの一括書き出し)、`components` / `skeleton` / `skeletons` / `rig` / `clip` / `clips` / `clipfit` / `skin`(10 章)を実装済み。今後 `export`、`index` を追加する。UI と同じライブラリを使うので、回帰テスト(全ブロック復号、全文字列件数)にも使う。

**既存ツールとの違い(漏れの原因だった点)**

- Deimos は英語のみ、かつ名前に `global` を含むパッケージのコンテナだけを読む。nim は全パッケージ・全 13 言語を読む。
- Destiny 系ツールが `cipher_shift` と呼ぶ SStringPart の 0x18 は、Marathon では **パートの種別** だった。上位バイトが種別、下位バイトが番号: `0x01nn` 位置引数 `{n}`、`0x0200` 変数 `{var:H}`、`0x0300` 入力ボタン `{input:H}`、`0x0500` ゲーム内の値 `{value:H}`。無視するとこれらの文字列から該当部分が黙って欠落する(英語だけで 692 文字列が空になっていた)。
- 言語スロットの順序は en, ja, de, fr, es, es-mx, it, ko, zh-cht, zh-chs, pt-br, pl, ru(実テキストで確認)。

**セリフの構造**: テーブル内の `Vec<S8080AA3B>`(0x28 バイト、0x20 にバリアントポインタ)→ `S8080AA3F`(0xA0 バイト。0x28 = 音声イベントの TagHash64、0x40 = 字幕の文字列ハッシュ、0x94 = 話者の文字列ハッシュ)→ hash64 テーブル → 音声イベント(class `8080B128`。0x20 = WEM の `Vec<Tag>`)。

**未対応**: 音声イベントは 24,229 件あるが、セリフテーブルから参照されるのは 2,597 件。台詞テーブルを経由しない掛け声などの音声は、別系統として P2 で調べる。

## 6. シェーディングテストの結果(nimshade)

`nimshade STATIC_TAG` は、静的メッシュの G-buffer パスを **ゲームの VS/PS(DXIL)を一切書き換えずに** D3D12 で描き、PS が出力した G-buffer 4 枚と簡易ライティングの合成を PNG に書く。無作為に選んだ静的メッシュ 48 個(全 57,022 個から)がすべて描画できた。1 メッシュあたり 0.4〜0.8 秒(パッケージ索引の構築を含む)。

**メッシュ**

- StaticMesh `80808635`: 0x08 = メッシュデータ Tag, 0x10 = グループごとの Technique `Vec<Tag>`。
- メッシュデータ `80808620`: 0x08 グループ(6 B: part u16, render_stage u8, input_layout u8)、0x18 パート(12 B: index_start, index_count, buffer, -, lod ビット, primitive)、0x28 バッファ(ib, vb0, vb1, color)、0x40 位置オフセット vec3、0x4C スケール、0x50 UV スケール、0x54 UV オフセット。
- render_stage: 0 = G-buffer、4 = シャドウ、13 = デプスプリパス。lod は 1, 2, 4, … 128 のビットで、1 が最高精細。
- 位置は R16G16B16A16_SNORM で `pos * scale + offset`。TANGENT は **クォータニオン**(VS がそこから法線・接線・従法線を作る)。

**G-buffer VS の入力(エンジンが用意するもの)**

- `t2` ByteAddressBuffer: インスタンスごとに 80 バイト。0〜47 = 3x4 行列(各行の w が平行移動)、+60 = メッシュブロックへのバイトオフセット。メッシュブロックは (offset.xyz, scale)、(uv scale, uv offset.xy)。
- TEXCOORD1(R32_UINT, インスタンス単位)= インスタンス番号。
- `cb12`(scope_view, 464 B): reg0〜3 = ビュー射影の列(絶対座標用)、reg7 = カメラ位置、reg19 = カメラ相対座標用の平行移動列。VS ステージの reg20 は View extern 0x40(ワールド → カメラ相対のオフセット = −カメラ位置。スキンメッシュの VS が使う)。VS はカメラ相対座標で計算する。PS と VS で cb12 のレイアウトが違う(view スコープのバイトコードがステージごとに別)。

**マテリアル(Technique `808031D8`)**

- ステージは 0x58 + i × 0x88(VS, HS, DS, GS, PS, CS)。各ステージ: 0x00 シェーダ Tag、+0x08 テクスチャ Vec(24 B: slot, WideHash)、+0x20 バイトコード、+0x30 バイトコード定数、+0x40 サンプラ、+0x50 **cbuffer の初期値**、+0x68 cbuffer スロット、+0x6C cbuffer Tag。
- cbuffer の中身はインラインの場合と、別バッファ(ヘッダ 32/7 → データ 40/7)の場合がある。後者ではインライン配列はレジスタ 1 個のダミー。これを読まないと多くのマテリアルが真っ黒になる。
- TFX バイトコードは cbuffer の初期値の上に書き込む。opcode 番号は Destiny 2 と同じだった(`src/content/tfx_vm.cpp`)。extern テクスチャ(`push_extern_texview` → `pop_texview`)は t7〜t18 など、エンジン側のテクスチャを差す。
- テスト用の PS(`80A65559`)は extern 0x61 から、ワールド座標に投影する 3 段のディテールレイヤ(行列 + 距離フェード)を受け取る。nimshade ではフェード距離を遠くに置いてベースマテリアルの経路を通している。

**G-buffer の出力(PS)**

| RT | 内容 |
|---|---|
| 0 | rgb = アルベド(リニア)、a = フラグ |
| 1 | rgb = `normal × (0.375 + smoothness / 8) + 0.5`(ワールド法線、長さにスムースネス) |
| 2 | マテリアルパラメータ(r = メタル系の値と推定、a = 1) |
| 3 | xy = モーションベクタ(前フレームとのクリップ座標の差 × 0.5) |

**ライティング(nim_render の LightingPass)**: G-buffer を読み、太陽の GGX(Smith 可視項, Schlick フレネル)、半球の空の放射照度、環境スペキュラ(Karis の EnvBRDFApprox)、RT2.g の発光をデコードして加算し、ACES で tonemap する。ゲームのシェーダではなく nim の代替。

**エンジンのライティングシェーダの調査(第一歩)**: ブートストラップパッケージ `013A`(`w64_client_bootstrap_patchable`)に 41/0(PS)521 個、41/6(CS)105 個のエンジン用シェーダがある(`nimcli extract 013A 41 DIR` → `dxc -dumpbin`)。入力が SV_Position だけのフルスクリーン PS のうち、`80A7432D` / `80A7433B` / `80A74326` は SV_Target を 2 枚(diffuse / specular の光の蓄積と推定)出し、t0/t1 を textureLoad、t3 に 3D LUT を持つ。cb12(view)に加えて cb0 を使い、reg23〜26 = 逆ビュー射影(画面 → ワールド)、reg27 = 光源位置、reg28 = 距離減衰(scale, bias)、reg32/34 = 方向・色、reg39 = 有効フラグで、ローカルライト(スポット/ポイント)の deferred シェーダとみられる。法線は `normalize(t1.rgb × 2 − 1)` と a > 0.5 のフラグで読んでおり、G-buffer RT1 そのものではなく、前段で作るライティング用の中間バッファを読んでいる可能性が高い。これらを実行するには、中間バッファを作るパスと cb0 の残りの意味の特定が必要。

**未解決**: ゲームのライティングパスは未実行で、合成画像は上記の代替。エンジンの extern / グローバルチャネルは既定値で埋めている。RT2 各チャネルの意味は未確定。

## 8. ゲームのライティングパス(GameLighting)

render globals(class `8080B61C` → `80808070`、`nimcli globals`)に、エンジンが名前で呼ぶパイプライン 700 本、スコープ 42 個、グローバルチャネル 203 個がある。nim はこのうち `global_lighting_and_shading`(technique `80A74245`)と `final_combine`(`80A7475B`)を、ゲームの DXIL のまま実行する(`src/render/game_lighting.cpp`)。

- **extern**: TFX の `push_extern_*` が読むエンジン側の状態。id ごとのバイト配列(float / u32 は 4 B 単位、vec4 / mat4 は 16 B 単位、texview は 8 B 単位)として持ち、既定値は goriath の定義に合わせた。View(2)、Deferred(3)、Frame(1)、GlobalLighting(42)、ShadowMask(43)、Atmosphere(7)、Postprocess(38) を nim が埋める。
- **スコープ**: view(`80A74035`、cb12)はステージごとのバイトコードを VM で実行する。frame(cb13)はバイトコードを持たず、エンジンが直接書く(時刻、露出、乱数シード …)。
- **ルートシグネチャ**: DXBC の PSV0 パートから各リソースの種別・レジスタ・次元を読んで組み立てる。サンプラはサンプラ Tag の参照先が D3D12_SAMPLER_DESC そのもの(52 B)なので、static sampler にする。
- **入力**: G-buffer(rt0〜2、深度)、light_diffuse / light_specular(ローカルライト未実装なので 0)、light_specular_ibl(nim の空の反射で代替)、BRDF のルックアップテクスチャ 4 枚(render globals)、影・AO(白で代替)。太陽は GlobalLighting 0x10 / 0x30、半球環境光は 0x70 / 0x80。シェーダが太陽に 1/(4π)、環境光に 1/4 を掛けるので nim 側で補正する。
- **高さフォグ**: シェーディングパスの中に 2 層の指数高さフォグがある。光学的厚さ = 0.001 × 距離 × Σ 密度ᵢ × exp(−0.001 × 減衰ᵢ × max(高さ − 基準ᵢ, 0))。透過率で表面を減衰し、t5 / t6(空のルックアップ: 近景・遠景)の色を足す。ゲームでは cb0[8, 13, 18, 40〜45, 104〜109] がマップの大気設定から来る。nim はここを上書きして UI から操作し、t5 / t6 は nim の散乱色で代替する。
- **final_combine**: 露出済み HDR に `x(1.04875x + 3.1344) / (x(0.99044x + 3.24045) + 0.65179)` の有理関数フィルムカーブを掛けて出力する(ガンマ込み)。nim の ACES はこれに置き換えた。
- **未実装**: 太陽の影(sdsm)、ローカルライト、空(`sky_*` パイプラインと sky lookup の生成)、大気ボリューム(`cascade_raymarch_atmosphere_volume*`)、キューブマップ、ブルーム、カラーグレーディング。

## 9. ダイナミックモデル(エンティティのメッシュ)

- SDynamicModel `8080881C`(2,366 件): 0x10 メッシュ `Vec`(0x88 B: vb0, vb1, -, -, ib, color, skinning, -, パート `Vec`, レンダーステージごとのパート範囲 u16[26], 入力レイアウト u8[25])、0xA0 位置スケール vec4、0xB0 位置オフセット vec4、0xC0 UV スケール、0xC8 UV オフセット。パート(0x28 B): technique、variant_shader_index、primitive(3 リスト / 5 ストリップ)、index_start、index_count、external_identifier(0x14)、lod(0x21、bit0 = 最高精細)。
- ストリップは 0xFFFF / 0xFFFFFFFF でリスタートする(PSO の IBStripCutValue)。
- **マテリアル**: パートの technique が none のものは、モデルを置くエンティティコンポーネント(class `8080BADB` 内の SDynamicModelComponent。0x234 = モデル、0x3D8 = technique_map {count, start, unk}、0x418 = techniques)から取る: `techniques[start + permutation % count]`。全コンポーネントを一度走査して索引を作る(約 0.5 秒)。
- **cb1(rigid_model スコープ)**: c0〜3 メッシュ → ワールド(VS が c3 から cb12[7] を引く)、c4 位置スケール、c5 オフセット、c6 UV、c7 動的 SH / AO、c12 / c13 = (offset.xyz, 1D スケール)、c14 = スキンストリームのオフセット。
- **スキン**: スキン用 VS は位置・法線を頂点 ID で t2 / t4(21/21/22 bit の snorm を u32 × 2)と t3(オクタヘドラル法線・接線)から読む。ゲームではコンピュートスキニングが毎フレーム書く。nim は vb0 のバインドポーズをこの形に詰めて渡す(goriath と同じ)。
- **アニメーション**: スケルトン・リグ・クリップ・スキンウェイトを解き、CPU スキニングで t2〜t4 を毎フレーム書き直して再生する(10 章)。

## 10. スケルトンとアニメーション

`src/content/animation.cpp`。エンティティ(class `8080BAAD`、0x08 = コンポーネントの `Vec`、12 B の先頭 u32 が Tag)が、モデルを置くコンポーネントと並べてスケルトンとアニメーションリグのコンポーネント(class `8080BADB`、0x18 のリソースのクラスで区別)を持つ。`index_model_skeletons` は全エンティティを走査して、モデル → (スケルトン, リグ) の索引を作る(リグを持つエンティティを優先)。

### 10.1 スケルトン(リソース `80809FB7`)

- +0xB0 ノード(16 B: ボーン名ハッシュ u32、親 i32)、+0xC0 バインドポーズ(オブジェクト空間)、+0xD0 逆バインド。変換は 32 B: クォータニオン xyzw、平行移動 xyz、スケール。親は子より前に並ぶ。
- 例: プレイヤー系のモデル `80B80191` はスケルトン `80B80190`(81 ボーン)。

### 10.2 アニメーションリグ(リソース `8080AD7E`)

クリップのボーン番号は **リグの番号** で、スケルトンの番号とは違う。

- +0xA8 ノード(72 B: ハッシュ u32、i16 × 4 = 親, −1, 空間の種別, 参照)。種別 0 / 1 はクリップの回転が **親に対するローカル**、2 / 6 は **オブジェクト空間** の回転。
- +0xB8 既定ポーズ(リグ順、32 B の変換)。+0xE0 スケルトン → リグ、+0xF0 リグ → スケルトンの u16 対応表。
- ポーズの組み立て(`pose_skeleton`): 回転はオブジェクト空間のボーンならクリップの値そのまま、ローカルのボーンなら親のオブジェクト回転 × クリップの値。位置は親 ∘ ローカルのバインド(バインドの骨の長さで FK)。ルート直下のオブジェクト空間ボーン(骨盤など)だけはバインド位置 + クリップの平行移動。ルートモーションは捨て、スケールは使わない。
- **加算クリップ**: 既定ポーズが単位回転でないオブジェクト空間ボーンの過半数が、フレーム 0 で単位回転のクリップは加算(エイムオフセットなど)とみなし、既定ポーズ × 差分(回転)、既定ポーズ + 差分(平行移動)で適用する(`is_additive`、`80B80191` のリグで 248 件)。

### 10.3 クリップ(class `8080AE01`)

- 0x140 = フレーム数 u16、0x142 = ボーン数 u16、0x120 = 名前ハッシュ。0xA8〜0xF8 の u16 `Vec` 6 本 = 定数トラックのボーン(スケール, 回転, 平行移動)と、アニメーショントラックのボーン(同順)。0x10 = 定数ブロック(`8080B13B`)、0x18 = アニメーションブロック。再生は 30 fps と仮定している。
- **sampled / 定数(`8080B13B`)**: u16 × 4 (3, S, R, T)、u32 フレーム数、スケールの (幅, 最小)、平行移動の幅 xyz・最小 xyz、u16 の値。トラック順・成分順のセクション [スケール][回転 ×4][平行移動 ×3]。回転は unorm16 を [−1, 1] に写す。
- **raw(`8080B13E`)**: u16 × 4 (2, S, R, T)、u64 フレーム数、u16 の値(同じ並び)、成分ごとの幅・最小の f32 `Vec`。
- **curve(`8080B13F`)**: トラックごとの u16 エントリ(0x70)。0x8000 以上なら毎フレームの値(0x10 の `~e` 番目から)、それ以外は 0x20 のブロック `e − 1`: 区間長のオフセット(0x30 の u8)、パラメータのオフセット(0x40 の u8)、区間数 n、n + 1 個のキー。区間長の合計 = フレーム数 − 1。区間ごとにチャネル 1 バイトのパラメータがあり、上位・下位ニブル(7 = 補正なし)で 3 次ベジェの内側の制御点 2 つを動かす。ニブル 1 段の大きさは **推定値**(1/1024、`kNibbleStep`)。回転キーは snorm16 の **(w, x, y)** で、|z| = √(1 − w² − x² − y²)、**x の最下位ビットが 1 なら z は負**。パラメータの 4 バイトは x, y, w, z チャネルの順。スケール・平行移動は unorm16 をトラックごとの範囲(0x50 幅、0x60 最小)に写す。
- 結果(install 全体): static 799、sampled 270、raw 1,852、curve 1,139 件をデコード。失敗 2 件(未知のブロック `8080B140`)。
- 検証(`nimcli clipfit 80B80191`): リグの既定ポーズからの回転の中央値は raw 35.5°、curve 36.2°。大腿 → 膝(リグ 3 → 4)の相対回転は raw・curve とも z 軸のヒンジになる(z の符号ビットを無視すると curve だけヒンジが崩れる)。

### 10.4 スキンウェイトと CPU スキニング

- スキンのメッシュでは vb0(24 B)の +6(i16 = w)がボーン指定: |w| < 0x800 なら 1 ボーン(番号 = w)。それ以外は skinning バッファ(メッシュの 0x30、u32 単位)の要素 `(|w| − 0x800) × 8 + (v << (w < 0 ? 1 : 0)) & 7` から、(ボーン, ボーン, 重み, 重み) の u8 × 4(w < 0 なら 2 要素で 4 ボーン)。ゲームのコンピュートスキニング CS の読み方に合わせた。ボーン番号は **スケルトンの番号**。
- スキン行列 = オブジェクト空間のポーズ × 逆バインド。nim は 3×4 行列の線形ブレンドで頂点・法線・接線を変換し、t2 / t4(位置)と t3(法線・接線)の形に詰めて、フレームごとのアップロードバッファ(`kFramesInFlight` 個)から DEFAULT ヒープのバッファへコピーする(`StaticMeshScene::set_skin_pose` / `update_skin`)。
- 詰めた位置は (位置 − offset) / range。ポーズで動いた頂点がはみ出さないよう、range をバインドの半径の 2 倍(`kSkinRange`)にし、cb1 の c12 / c13.w にも同じ値を入れる。
- UI: ENTITIES タブでリグを持つスキンモデルを開くと「アニメーション」パネルが出る(クリップの選択、再生 / 一時停止、前後、フレーム、速度)。`nimshade --clip CLIP [--frame F]` で同じポーズをヘッドレスで描ける。
- 未対応: ルートモーション、スケールトラック、クリップのブレンド、エンティティ(パターン)とクリップの正式な対応付け(今はリグのボーン数が同じクリップをすべて並べている)、`8080B140` コーデック。
